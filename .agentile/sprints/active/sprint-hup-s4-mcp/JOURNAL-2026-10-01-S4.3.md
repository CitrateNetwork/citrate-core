# Journal: wiring two read-only servers that each had a reason not to work

**The explorer was read-only but never said so.** CitrateScan's MCP server is read-only by
construction, and its discovery manifest even says `readOnly: true`. But MCP tool annotations
are per tool, and the server sent none. The S4.1 host follows the spec: no `readOnlyHint` means
"may write", and write tools are off by default. So pointing Hermes at the explorer would have
connected cleanly and offered zero tools. The fix was in the explorer, not the host: annotate
every tool. A protocol-level claim the client cannot see is not a claim.

**The memory daemon speaks the right protocol on the wrong pipe.** mem-mcp is a Unix-socket
daemon; the S4.1 host speaks stdio or HTTP. Rather than add a socket transport to the host (a
runtime change for one server) or ship a second binary (packaging work across three
platforms), core runs itself as the bridge: the allowlist names the citrate-core executable
with a distinctive flag, and `main.rs` hands off before any app start-up. The bridge is also
where the read/write line is drawn: mem-mcp's tools carry no annotations either, and four of
them write. Core knows which are which, so core filters and annotates, and a write call never
reaches the socket.

**What surprised me.** The parity fixture is byte-pinned across two repos, so adding one core
tool is a three-repo change (core, runtime fixture copy, and the sha in both). That is the pin
working as designed, and it is a likely merge conflict for any other lane adding a tool in the
same fan-out.

**What I would do differently.** I would have read the production explorer's `/api/mcp`
discovery output before planning. The missing annotations were visible there in one request.
