# Journal: the file llama-server reads is not the file you checked

The first gate hashed the adapter the member pointed at, compared the scorecards, and on
ACCEPT passed that same path to llama-server as `--lora`. The tests were green: a swapped
file between the gate and the load was caught by re-hashing at load time.

Writing `FlRoundGate.tla` meant writing down every action that reads the file, and one of them
was not in the tests: the supervisor restarting llama-server after a crash. It reuses the same
argv, so it re-reads whatever sits at that path at that moment. A check at load time protects
the load, not the next restart. The fix was to stop serving the member's file at all: copy the
verified bytes into the app's own store under their hash, re-hash the copy, and point `--lora`
there. The mutants for "serve the source" and "skip the re-hash of the copy" both die on
`ServedIsLoaded`.

The model found a second gap on its first run. Gate records are keyed by hash and the latest
one wins, which is right for a REJECT. But an ACCEPT measured on a different base model also
replaced the record of an adapter that was loaded on this base, and nothing unloaded it. The
code only unloaded on REJECT. Now any new record that no longer allows the served adapter on
the served base unloads it.

The other lesson is about "start". The coordinator has no endpoint for starting a round; jobs
come from an operator's catalogue, and workers sign their own leases. So the honest version of
"Hermes starts a round" today is: the member approves one exact plan, core re-reads the
coordinator and records that approval, and the receipt says no training ran because the worker
is not in this build. Making that sentence part of the receipt, the tool result and the panel
was cheaper than explaining later why a "started" round never trained.
