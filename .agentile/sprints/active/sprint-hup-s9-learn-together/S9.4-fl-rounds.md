# HUP-S9.4: Hermes plans, explains and starts federated rounds

Planset: `.agentile/planset/2026-09-30-hermes-upskill/` (02_ARCHITECTURE section 9 "Hermes can
plan, explain, and (under HIC-1) start rounds"; 04_FEATURES_BDD US-9.1 AC5 "loadable by
llama-server and improves the eval score, or is rejected by the eval gate"; 05_SPRINTS_AND_WPS
S9.4).

## Data sources (Rule 7)

| Surface | Source |
|---|---|
| Coordinator state | citrate-compute-pool training-coordinator `GET /v1/status` (`{counts:{pending,leased,done,quarantined,workers}, settlement}`) at the configured base URL |
| Coordinator URL | `CITRATE_FL_COORDINATOR_URL` (operator override), else the member's setting in `<app data>/fl_rounds.json`; no default |
| Device fit | `tier::probe` (local, no network) |
| Eval gate | the JSON scorecards from `scripts/eval-tools.mjs` and `scripts/eval-qa.mjs` (deterministic scorers in `src/agent/eval/`) |

## What shipped

- **Core module** `src-tauri/src/fl_rounds.rs`. Coordinator URL validation (https, or http on
  loopback only; no credentials, query or fragment). Strict `/v1/status` parser: missing or
  mistyped fields are errors, never zeroes; only counts and one of `shadow | live | unknown`
  leave it. Pool phase from counts (no work, open, running, complete).
- **Plan + explanation.** `build_plan` answers data, compute, reward and privacy in plain words,
  plus a status line and the blockers: no coordinator, unreachable, no open work, H-01 (operator
  vetted only), federated work on a device without a known accelerator. The data paragraph says
  the verified-trajectory export (S9.3) is not wired into core yet. The plan hash binds the
  proposal, the coordinator URL and status read, and the base model.
- **HIC-1 start.** The member approves a card showing that plan (no signature, no wallet).
  `start_round` then requires a plan core built in the last 15 minutes, refuses a second start
  of the same plan, re-reads the coordinator and refuses if the work is gone or the settlement
  mode changed. It records the authorization in `fl_rounds.json`. The receipt says plainly that
  this build has no device training worker, so no training started.
- **Eval gate.** `fl_adapter_gate` hashes the adapter (SHA-256, streamed), checks the GGUF
  magic and the expected hash, reads the base and candidate scorecards, and decides. The runs
  must be comparable (same model, dataset version, n), the base run unstamped and the candidate
  stamped with this adapter's hash (`--adapter-sha256`, new on both eval CLIs). ACCEPT only if
  no metric got worse and the mean of the shared metrics strictly improved. Records are keyed by
  hash and the latest decision wins.
- **Load.** `fl_adapter_load` needs ACCEPT for the served base, copies the file into
  `<app data>/adapters/<sha256>.gguf`, re-hashes the copy and restarts llama-server with
  `--lora` pointing at it (the supervisor re-reads `--lora` on every crash restart, so the
  member's original file is never served). A base-model switch drops the adapter. A new gate
  record that no longer allows the served adapter unloads it.
- **Hermes tools.** `fl_round_plan` (read) and `fl_round_start` (write, HIC-1 card; a
  `hic:"required"` reason rides the same card). Both system prompts mention them. The
  toolcall and injection eval sets gained four tasks and one injection case (appended,
  revisions noted); the parity fixture's tool roster gained the two tools in both repos.
- **UI.** `FlRoundsPanel` on the Train surface: coordinator setting (with the honest "no
  coordinator is configured" text), plan and the four answers, Join (disabled with blockers),
  the eval-gate form, Load only on ACCEPT, the loaded adapter and Unload.
- **Formal.** `formal/FlRoundGate.tla`: StartOnlyApproved, StartOnlyWhatWasApproved,
  AtMostOneStart, LoadedIsAccepted, ServedIsLoaded. TLC green (881,600 distinct states, depth
  15); both reach configs violated as expected; 13/13 mutants killed. The first draft found a
  gap (a served adapter re-gated as ACCEPT against another base stayed loaded), fixed by
  `must_unload_after_gate`.

## Not done here

- Live rounds: no coordinator is deployed for members and the device training worker is not
  bundled (S9.1/S9.2, DGX). Start records approval only.
- Adapter download from LoRAFactory / ModelRegistry: not deployed on 40204 (F-4). The gate
  takes a local file and its published hash.
- Running the candidate eval in the app: the member or operator runs the eval CLIs against a
  llama-server started with `--lora` (see below). The app gates on the resulting scorecards.
- The trajectory export (S9.3, runtime `agent-trajectory`) is not wired into core.

## Producing the candidate scorecards

```sh
# base
node scripts/eval-tools.mjs --base-url http://127.0.0.1:18080/v1 --model <base> --tier T1
# candidate: llama-server -m <base>.gguf --lora <adapter>.gguf --jinja ... on the same port
node scripts/eval-tools.mjs --base-url http://127.0.0.1:18080/v1 --model <base> --tier T1 \
  --adapter-sha256 $(shasum -a 256 <adapter>.gguf | cut -d' ' -f1)
```

The candidate file is written as `<date>-<model>-lora-<first 12 hex>.json`, so it never
overwrites the base run.
