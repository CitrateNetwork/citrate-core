# Journal: two components, one price

The escalation router is split across a process boundary on purpose. Core owns the budget and
the key; the sidecar owns the call. That split has a cost: both sides compute the worst-case
price, and they have to agree to the micro-dollar. The sidecar refuses any request whose
reservation is below its own worst case, because that refusal is what lets it promise "a
settled charge never exceeds what the budget already holds".

The first core quote disagreed with the sidecar by 48 micro-dollars. Core counted the absent
system prompt as an empty message (16 tokens of template overhead at $3 per million), and the
sidecar did too, but the wire body omitted it. Neither unit suite caught it alone, because each
side was internally consistent. The fix was to count only messages actually sent, in both
repos, and to pin one shared golden value (152 micro-dollars for "Plan it.", 64 tokens, $1/$2)
in a test on each side, each naming the other.

The second thing the model made explicit was the cap itself. "Over budget asks the member" and
"spend never exceeds the cap" sound like they conflict. They stop conflicting once a confirmed
escalation is treated as what it is: the member's own decision for one request, recorded
separately and never counted against the budget. `OverBudgetOrTaintedNeedsHic1` and
`SpendWithinCap` then hold together, and mutants M01 and M07 show each guard is needed.

Lesson worth keeping: when a check is duplicated across a boundary for defense in depth, pin a
cross-repo golden at the same time, or the two copies drift silently.
