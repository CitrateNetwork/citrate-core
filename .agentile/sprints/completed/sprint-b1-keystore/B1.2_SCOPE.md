# B1.2 — SignatureCeremony (the one HITL signing path; lifts Rule 3)

## What B1.2 is
B1.1 put a real key in the vault and proved an in-process sign (`wallet::sign_message`, a
plain `pub fn`, NOT a command). B1.2 makes that signer reachable **only** through a single
human-in-the-loop **SignatureCeremony**: every signature intent — from the user, and later
from node-agent / chat-agent / micro-apps — routes through one approval surface, and nothing
is signed without an explicit, per-request human approval. **This LIFTS Rule 3** (CLAUDE.md):
until now "no signing code paths"; after B1.2, "all signatures via the SignatureCeremony,"
and signing outside it is forbidden.

## What B1.2 is NOT
- Not the wagmi/EIP-1193 connector (that is B1.3 — it will CALL the ceremony).
- Not a real broadcast tx to 40204 (B1.4).
- Not allowlist/auto-approve rules, multi-account, or agent-origin wiring (later).

## Design
- **`SignatureIntent { origin, kind, decoded, chain_id, raw }`** — `kind` ∈
  {`personal_sign`, `typed_data`, `transaction`}; `decoded` = human-readable
  `{ action, cost, destination }`. Built from any origin; the origin string is set by the
  caller/bridge and displayed verbatim (never trusted to be benign).
- **Ceremony state machine (Rust core):**
  - `request(intent) -> CeremonyId` — creates a PENDING ceremony, decodes the intent for
    display, **does NOT sign**. Returns the id + the decoded view.
  - `approve(id) -> Signature` — only if the ceremony exists AND is pending AND (for
    undecodable calldata) a raw-mode ack was given; unwraps the key via the B1.1 vault path,
    signs (`wallet::sign_message` for messages; `chain::sign_secp256k1` for the recoverable
    EIP-155 tx form), zeroizes, and **consumes** the ceremony (single-use). Returns the
    signature ONLY — never key material.
  - `reject(id)` — consumes the ceremony, no signature.
- **The signer is gated:** `wallet::sign_message` / the tx signer become `pub(crate)` and are
  called ONLY from `approve`. No other code path signs. No sidecar/agent/daemon signs
  (node-agent emits an unsigned intent → a ceremony).
- **Command surface (invoke):** `sign_request`, `sign_approve`, `sign_reject` ARE
  `#[tauri::command]` (they return a ceremony id / decoded intent / signature / status) but
  **NONE returns key/seed/entropy material** (I-2 — keep the compile-time barrier from B1.1).
- **Approve is never default-focused / one-click:** UI does not pre-select Approve; backend
  requires an explicit approval bound to the specific `CeremonyId` (no "approve latest",
  no auto-approve).
- **Undecodable calldata:** if the intent can't be decoded to a human action, the ceremony
  surfaces `Unrecognized`/raw and `approve` is BLOCKED until an explicit raw-mode ack — never
  silently approvable as if benign.
- **Vault unlocked required; fails closed if locked** (inherits B1.1 / A2 session gate).

## Integration test
- request → decoded intent surfaced (no signature yet) → approve → signature ecrecovers to
  the wallet address; a second approve on the same id → error (consumed); reject → no
  signature; approve on unknown id → error. Against the real B1.1 vault (FakeKeyring headless).

## Acceptance (Rule 11 — named sources)
- `sign_request` returns a pending CeremonyId + decoded intent, NO signature (state inspection).
- `sign_approve` on a pending ceremony → signature that **ecrecovers to the wallet address**
  (data source: k256 recover); on consumed/unknown id → error.
- No signing reachable without an approved ceremony (source-scan of signer call-sites +
  command-registry enumeration).
- Undecodable calldata → approve blocked without raw ack (data source: intent decode).
- Locked vault → approve fails closed (data source: session state).
