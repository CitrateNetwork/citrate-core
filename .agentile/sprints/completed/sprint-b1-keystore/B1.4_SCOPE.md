# B1.4 — real 40204 broadcast through the ceremony (option A)

## Decision locked (owner, 2026-07-13)
**Option A:** expose a lean EIP-155 recoverable-sign primitive UPSTREAM in wallet-core's
`crypto` feature (B1.4.0), keeping all signing crypto in the shared, audited crate — rather
than re-deriving v/r/s in citrate-core.

## Why the primitive isn't already lean
`wallet-core/src/chain.rs` (`TransactionBuilder::sign_secp256k1` → EIP-155 v/r/s) is sound,
but the whole `chain` module is `#[cfg(feature="native")]` because it also carries an
`RpcClient` (`reqwest`) and imports `citrate_consensus` (which drags ark-*/tracing-subscriber
— the exact stack B1.1-F-1 stripped from the key path). The **signing** part uses only
`sha3::Keccak256` + `k256` recoverable ECDSA + `rlp` — all lean-available. B1.4.0 extracts
the pure signing into `crypto`; the RPC/consensus bits stay `native`.

## B1.4.0 (UPSTREAM, citrate-chain/wallet-core) — lean EIP-155 recoverable signing @rule8
Separate build-and-stop + INDEPENDENT review (like B1.1.0). Do NOT bundle into citrate-core.
- Expose under the lean `crypto` feature a pure function, e.g.
  `sign_eip155_legacy_tx(key: &SigningKey, tx: LegacyTxFields, chain_id: u64) -> Result<SignedTx>`
  where `SignedTx { raw: Vec<u8> /* RLP, ready for eth_sendRawTransaction */, hash: [u8;32], v,r,s }`.
  Also (optional) `sign_recoverable(prehash) -> (r,s,recovery_id)` if cleaner.
- Reuse the existing keccak + RLP + `v = recovery_id + chain_id*2 + 35` logic; do NOT pull
  `reqwest`/`tokio`/`citrate_consensus`. Keep the existing native `chain` module (RpcClient,
  ed25519/consensus path) intact for desktop/CLI consumers.
- Zeroize any intermediate secret material (WAL-04 pattern).
- **Acceptance (Rule 11 — named vector):** for a known key + known legacy tx fields, the
  produced signed raw tx **ecrecovers to the signer address**, and v/r/s match a reference
  (cross-check the RLP + `v` against an ethers.js/viem-produced signed tx for identical
  inputs; assert byte-equality of the raw tx OR at minimum sender-recovery + EIP-155 `v`).
- No regression: native/default build + existing chain tests still pass; `cargo test`
  monotone; lean build compiles WITHOUT the heavy chain; `cargo audit` stays clean on lean.

## B1.4 (citrate-core) — broadcast the transaction the ceremony approved
After B1.4.0 merges + citrate-core re-pins the lean feature to the new rev (Rule-12 drift).
- **Ceremony `transaction` path signs for real:** `ceremony::approve` for a `transaction`
  intent decodes the tx fields, builds them, calls the lean `sign_eip155_legacy_tx` with the
  vault-unwrapped key (in-process, zeroize), and returns the signed raw tx. Still single-use,
  raw-ack-gated for undecodable calldata, fail-closed when locked — all B1.2 invariants hold.
- **Broadcast:** citrate-core sends the raw tx to the live 40204 RPC (`eth_sendRawTransaction`)
  and polls the receipt (`eth_getTransactionReceipt`) for inclusion. The wagmi connector's
  `eth_sendTransaction` (B1.3's 4900 deferral) now returns the real tx hash after ceremony
  approval + broadcast.
- **Prove it (Rule 11):** a real 40204 tx, **signed through the ceremony and confirmed by
  block inclusion** (data source: 40204 RPC receipt). Also: the sender == the wallet address;
  a message sign still ecrecovers (B1.2 unbroken).
- Decode the tx intent into human-readable {action, cost, destination} for the ceremony
  display (B1.2 currently marks `transaction` undecodable/raw — B1.4 adds real legacy-tx
  decoding so the human sees what they approve; undecodable variants still raw-gate).

## ⚠️ OWNER INPUT NEEDED for the B1.4 on-chain proof
A **confirmed** 40204 tx needs a **funded account** (gas). The signing/broadcast path can be
proven to reach the node without funds (well-formed raw tx accepted / "insufficient funds"
from the node proves the round-trip), but "confirmed by block inclusion" (the S2.1 acceptance)
needs SALT for gas on the wallet's derived address. Owner decision — see the ask below.
