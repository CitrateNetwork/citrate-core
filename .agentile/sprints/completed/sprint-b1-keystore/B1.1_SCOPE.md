# B1.1 — wallet keystore into the hardened vault (grounded scope)

## The two owner decisions this scope is built on
- **D-B1.1-1 (locked): A2 vault is the SOLE custody root; wallet-core is a crypto library.**
  We do NOT use `KeyManager` (its `keys.json` persistence, `unlock`, `save`, `session.rs`
  lockout, or its Argon2id password domain). The seed is sealed in the A2 vault; wallet-core
  is used only for BIP39, HD derivation, `UnifiedKey`/secp256k1 signing, address derivation,
  and `chain.rs` EIP-155 tx signing. One store, one unlock domain (the vault passphrase),
  one lockout (A2's, already hardened over 4 review rounds).
- **D-B1.1-2 (locked): re-add standard BIP44 secp256k1 HD derivation UPSTREAM in
  citrate-wallet-core (B1.1.0), then integrate.** The crate today CANNOT produce a
  mnemonic-recoverable secp256k1 EVM key — `secp256k1_secret_from_seed` was deleted as dead
  code (WAL-10/RM-G2.2, `keys.rs:650`); secp256k1 keys are random-only (`mnemonic:
  String::new()`, `keys.rs:424`) and the mnemonic path yields a non-standard Ed25519 key
  (`seed[..32]`, `recover_from_mnemonic` `keys.rs:346`). Without HD derivation, D-B1-1's
  "the BIP39 seed is the recovery" premise is empty. The removal comment itself prescribes
  BIP32 HD derivation "via a proper sprint when EVM mnemonic recovery is on the roadmap" —
  this is that sprint. Removal was benign (dead code, no security defect), so re-adding
  reopens no prior finding.

## Grounded facts about the real crate (cite, don't assume)
- `UnifiedKey::Secp256k1(k256::ecdsa::SigningKey)` — the signing primitive. `sign(&[u8])`,
  `derive_address()` (Keccak-256(uncompressed_pubkey[1..])[12..32], EVM-compatible),
  `public_key_bytes()`, `secret_bytes() -> [u8;32]`. (`keys.rs:96-160`.)
- `chain.rs::TransactionBuilder … sign_secp256k1(&SigningKey, nonce) -> SignedTransaction`
  produces proper **EIP-155 v/r/s** (`v = recovery_id + chain_id*2 + 35`) — 40204 tx signing
  already works once we hold a secp256k1 key. (`chain.rs:126`.)
- Keystore entries bind AAD `citrate-keystore-v2 || kdf_version || key_type || address`
  (WAL-02) — we are NOT using that keystore (Option A), but B1.1.0 must not regress it.
- Crate deps include `citrate-security = { path = "../core/security" }` — a **path dep** that
  will not resolve when citrate-core consumes wallet-core from another repo. Packaging must
  be solved (see B1.1 WP-0).

- **WP-1 — seed sealed in the A2 vault, `wallet-` reserved slot.**
  - Create: generate a 24-word BIP39 mnemonic; derive the secp256k1 `UnifiedKey` via the
    B1.1.0 HD path; seal the **BIP39 entropy/seed** into the A2 vault under a
    **backend-reserved `wallet-` slot prefix** (mirror the `oidc-` reservation + the A3-01 /
    DR-3 guard so a webview `custody_put` CANNOT write/plant `wallet-*`). Store the derived
    address + public key (non-secret) for display.
  - Requires the vault UNLOCKED; **fails closed** if locked (mirror A3 refresh-slot pattern).
  - **Show the mnemonic exactly once at create for backup** (the recovery per D-B1-1); never
    persist it in plaintext, never log it, zeroize after display-confirm.
  - Acceptance: after create, a raw-bytes scan of `custody.enc` finds **no** seed/entropy/key
    plaintext (data source: the custody raw-grep probe); the sealed slot is `wallet-`-prefixed.
- **WP-2 — import + derive.** Import a user mnemonic → derive the same secp256k1 address →
  seal. Acceptance: importing the B1.1.0 canonical vector yields
  `0x9858EfFD232B4033E47d90003D41EC34EcaEda94` (data source: the published BIP44 vector).
- **WP-3 — in-process sign round-trip proof (NO ceremony/command yet — that's B1.2).**
  vault unlock → pull sealed seed in-process → derive `UnifiedKey` → sign a message →
  ecrecover == address; zeroize. Acceptance: `ecrecover(sig) == derived address` (data
  source: k256 recover). No `#[tauri::command]` returns the seed/key (enumerate the registry).
