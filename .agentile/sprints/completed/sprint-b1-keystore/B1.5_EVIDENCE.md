## 2. WP-2 — the two carried should-fixes

### F-1 (from B1.4 review / citrate-security #23) — extend the signer guard to `sign_transaction`
- **Change:** `adv1_adv7_signer_only_reachable_via_approve`
  (`ceremony_tests.rs:202`) now scans for BOTH `sign_message(` AND
  `sign_transaction(` invocation forms across the real crate sources (added
  `rpc.rs` + `txdecode.rs` to the scanned set), asserts BOTH are invoked from
  ceremony.rs (positive control), and asserts BOTH are `pub(crate)`, never `pub`.
- **NEGATIVE CONTROL (reproduced):**
  1. Injected `let _ = crate::wallet::sign_transaction(vault, &fields, 40204);`
     into `seam.rs` (a non-ceremony module). The guard test FAILED with:
     `seam.rs: a gated signer is invoked outside ceremony approval:
     \`let _ = crate::wallet::sign_transaction(vault, &fields, 40204);\``.
     Removed the injection → green. **DID sign_transaction injection get caught:
     YES.**
  2. Widened `pub(crate) fn sign_transaction` → `pub fn sign_transaction`. The
     guard test FAILED with: `the transaction signer must be pub(crate)
     (crate-private), never pub`. Restored `pub(crate)` → green.
- **Result:** both signers are reachable ONLY from ceremony approval; the tx
  signer is no longer structurally ungated. ADV-1/ADV-7 now cover both.

### F-2 (from B1.4 review) — assert `from == wallet` before nonce-fetch/sign
- **Change (`ceremony.rs`):** new `CeremonyError::FromMismatch { claimed, wallet }`
  (Display + secret-free — carries only the two PUBLIC addresses). In
  `approve_and_broadcast`, immediately AFTER the tx decode and BEFORE the
  nonce/gas fetch and sign: if `parsed.from` is present, look up the vault wallet
  address (`wallet::address`) and compare case-insensitively; on mismatch return
  `FromMismatch` — sign nothing, touch no RPC. An ABSENT `from` is left to the
  existing nonce block (a dApp omitting `from` must supply a nonce, else
  `UndecodableTransaction`) — no wrong-sender tx can be produced without a `from`.
- **Both branches tested:**
  - MATCH: `b1_5_f2_from_matching_wallet_proceeds_to_broadcast`
    (`ceremony_tests.rs:1152`) — `from == canonical wallet` → signs + broadcasts;
    RPC IS reached (happy path not regressed).
  - MISMATCH: `b1_5_f2_from_mismatch_fails_closed_before_sign_or_broadcast`
    (`ceremony_tests.rs:1180`) — spoofed `from` → exact `FromMismatch` variant
    with the claimed + actual addresses; **no RPC touched at all** (not a nonce
    fetch, not a broadcast — proven by asserting the mock's recorded-requests list
    is empty); ceremony consumed (fail-closed single-use).
  - `b1_5_f2_from_mismatch_error_is_secret_free` (`ceremony_tests.rs:1237`) — the
    variant carries no mnemonic/key, only the two public addresses.
- **NEGATIVE CONTROL (stated):** removing the `parsed.from == wallet` assertion
  makes the mismatch test flip — the mock WOULD be hit (nonce fetch), the vault
  WOULD sign, and the failure would surface downstream (node/broadcast error or a
  wrong-sender tx) instead of a clean pre-sign `FromMismatch`.
- **Note on the locked path:** the F-2 `wallet::address` lookup is itself
  unlock-gated, so a locked mismatch-check fails closed via the normal
  `WalletError → CeremonyError` map (VaultLocked/NoWallet) — F-2 preserves ADV-3.

## 3. WP-3 — residual triage

### B1.2 R2 — locked vault surfaced as `NoWallet` not `VaultLocked` → **FIXED (cheap)**
- **Decision:** fix, not accept. It is cheap AND improves the ADV-3 signal.
- **Change (`wallet.rs::read_entropy`):** on a `custody_get` `Denied`, consult
  `vault.is_unlocked()`. Locked → `WalletError::Custody` (→ `VaultLocked`,
  "unlock" hint). Unlocked-but-denied → `WalletError::NotFound` (→ `NoWallet`,
  "create a wallet" hint).
- **Why this adds NO oracle:** `is_unlocked()` reflects only the SESSION boolean
  — passphrase-INDEPENDENT and already observable on the invoke surface via
  `custody_status`. The custody crypto property (no wrong-vs-empty passphrase
  oracle, `custody_get` opacity) is UNTOUCHED. This is a UX-layer distinction in
  the wallet module, not a custody-layer one.
- **Test:** `b1_5_r2_locked_approve_surfaces_vault_locked_not_no_wallet`
  (`ceremony_tests.rs:394`) proves a locked approve on a wallet-bearing vault now
  surfaces `VaultLocked`, and an UNLOCKED empty vault still surfaces `NoWallet`.
  The prior fail-closed tests (which match `NoWallet | VaultLocked`) still pass.

### B1.3 per-request origin capture (INFO) — **noted, no change**
The connector captures the origin at provider-construction time
(`window.location.origin`), correct for today's single-origin desktop shell. A
future multi-dapp / embedded-micro-app host should capture the TRUE per-REQUEST
caller origin instead (so one shell hosting several origins cannot mislabel). Not
trivial to do faithfully today (there is one origin), and not security-load-bearing
in the single-origin shell — deferred to the multi-dapp phase. No code change.

### B140-2 (upstream wallet-core RLP payload zeroize) (INFO) — **out-of-repo, no change**
Zeroizing the intermediate RLP signing payload is defense-in-depth inside
`citrate-wallet-core` (the pinned crypto lib), not citrate-core. Per scope, NOT
touched here. Flagged for the wallet-core repo. (Related: the wallet-core signer
already zeroizes its intermediate signing-HASH buffer — WAL-04.)

## 4. Honest non-headless gaps (stated, not faked)

1. **Live OS keyring.** All adversarial crypto/session/lockout/tamper tests run
   against an in-memory keyring FAKE — a live platform secret service cannot run
   in headless CI. The real `OsKeyring` seam is exercised by
   `custody_tests::real_keyring_roundtrip_or_skip` (`custody_tests.rs:460`), which
   round-trips against the real keyring IF reachable and otherwise SKIPS with a
   printed note (never fakes a pass). F-1(B1.0)/F-1b anchor-deletion tests run the
   whole attack headless because the injected fake holds both the anchors and the
   master.
2. **Interactive approval UI.** ADV-6's pixel-level default-focus / one-click
   property is UI and not headless-testable. The CORE contract (approval bound to
   an explicit `CeremonyId`; no "approve latest"/auto-approve API) IS proven
   (`ceremony_tests.rs:525`). The JS connector's approval hook fails CLOSED by
   default (never auto-approves) — `defaultApprovalHook` returns `null` (reject).
3. **Live-broadcast HITL gesture stood-in.** In the live end-to-end proof the
   human approval CLICK is stood in for by calling `approve_and_broadcast`
   programmatically. The SIGNING + BROADCAST + on-chain confirmation are fully
   real; only the click is stood in (stated in the test comment).
4. **ADV-9 memory-residue.** Proven to the type/teardown contract, NOT a physical
   byte-wipe (post-drop reads are UB). A MIR/LLVM zeroize-audit pass is DEFERRED
   before real wallet keys ship at scale (BND-4).
