# Skill-intake review, 2026-09-30 (HUP-S3.6)

Every third-party skill that the planset names for the bundled Hermes corpus (S3.1: Trail of
Bits, frontend-skills, agentile, curated hermes-fork skills) was reviewed for provenance,
licence, loader validity, size, bundled executables, and prompt-injection or exfiltration
patterns. Each skill got one verdict. `skills.lock` records the source commit, the path, the
sha256 of `SKILL.md` and of every file that ships, the files that are stripped, and the verdict.
No skill content is copied into this repo.

296 skills across 5 sources. **111 can ship**: 100 as-is, 9 with executables stripped, and 2 with
scripts stripped until a named capsule replaces them. **185 are excluded**: 174 hermes skills and
1 frontend skill because the runtime loader refuses their frontmatter, and 10 Trail of Bits skills
on review.

Key findings:

1. **No hermes-fork skill loads.** All 174 use frontmatter the strict S3.2 loader refuses: a
   nested `metadata.hermes.{tags,related_skills}` map (157), top-level `platforms`, `author`,
   `tags` or `requires` keys (15), or a `SKILL.md` over 64 KiB (2). Most also carry `author` and
   `platforms` below the first error. Nothing from hermes can be curated until an owner picks a
   fix (see "Owner decisions"). Every hermes skill is in the lock as `exclude` with its SKILL.md
   hash, so a later normalization pass starts from a pinned baseline.
2. **Executables hide outside `scripts/`.** The loader flags only `scripts/`. Six loader-valid
   skills also carry `.sh`, `.py`, `.js` files or a `Dockerfile` under `resources/`, `tools/`,
   `examples/` or `assets/` (one has 25). The intake treats any file with an executable extension,
   a `Dockerfile` name or a `#!` first line exactly like a script: stripped and not hashed as a
   shipped file.
3. **Loader parity is exact.** The generator's frontmatter and file-listing rules are a JS port of
   `agent-loop/src/skills.rs`. Run against all 296 skills, the port and the real Rust loader (a
   scratch harness linking `citrate-agent-loop` at runtime `hup/s3-skill-loader@2c13b89`) agree on
   296/296: same accept/refuse, same refusal reason, same ref list, same script list.
4. **The Trail of Bits snapshot is upstream-exact.** The vendored tree in citrate-labs `.claude/`
   has every blob under `plugins/` identical to trailofbits/skills `a56045e9` (2026-05-06). Only
   `.github/` files and one `uv.lock` differ. Upstream `main` is 93 commits ahead today (R-12).
5. **No cross-source name collisions** among shipped skills.

## Verdict rules (method)

- **Provenance.** Each source is pinned to a full upstream commit. For git checkouts the commit is
  the checkout `HEAD`. For the vendored ToB tree, a bare clone of trailofbits/skills was searched
  for the commit whose `plugins/` blobs match the vendored tree. Pins live in
  `.agentile/skill-intake/intake.json`.
- **Loader validity.** The frontmatter and size caps are the S3.2 loader's (64 KiB SKILL.md, name
  `[a-z0-9-]{1,64}` matching the directory, description ≤1024 chars, strict YAML subset, unknown or
  duplicate keys refused, 128 KiB per ref, 64 listed files, depth 4). A skill the loader refuses
  is `exclude`; shipping it would only produce a load-time rejection.
- **Executables.** `scripts/` plus any executable-looking ref (see finding 2) are never shipped.
  If a skill keeps working without them it is `include-with-scripts-stripped`. If its body is a
  wrapper around them it is `exclude`. If the executable is pure and worth keeping it is
  `convert-script-to-capsule` with a named capsule (WASM, signed, behind the ApprovalQueue).
- **Content scan.** Every SKILL.md body, text ref and executable is scanned for red flags:
  pipe-to-shell installers, safety/approval-disable instructions, known exfiltration endpoints,
  credential paths. Notes are also recorded and do not block: network installs, remote fetches,
  shell blocks, destructive shell, secret env names. **A red flag on a skill that would ship blocks
  the generator until a decision with a reason is recorded in `intake.json`.** A decision for a
  skill that no longer exists also fails the run, so reviews cannot go stale silently.
- **Relevance.** A few skills are excluded on merit: they conflict with a locked HUP decision or
  target another agent host. Each one has its reason in the lock.
- **Hashes.** sha256 of `SKILL.md` for every skill, excluded ones too, so any upstream change shows
  as drift and forces a re-review. sha256 of every shipped ref. Stripped files are listed by path
  only.
- **Reproduce.** `node scripts/skills-lock.mjs --check` (sources base defaults to the directory
  above the repo, which is the citrate-labs tree; override with `--sources-base` or
  `SKILLS_SOURCES_BASE`). `--table` prints the per-skill table below. The vitest suite
  `scripts/skills-lock.test.mjs` recomputes the lock from the sources when they are on disk and
  fails on any byte of drift. Where they are absent (CI), it still checks the committed lock's
  structure.

Limits of the method: the scan is pattern-based. It caught every case a manual read of the
flagged files confirmed, but a rephrased injection would pass it. Each red-flag hit on a skill
that ships was read by hand. The rest of the shipped bodies were reviewed by description and scan
notes, not line by line. The S1.10 injection eval set and the S11 red-team are the backstop.

   `metadata.<ns>.<key>` map and record `platforms`, `author`, `tags` and `requires` as tolerated
   extension keys. Option (b): normalize hermes frontmatter at intake into the strict subset (MIT
   allows it) and lock the normalized hashes. Either way, curation of which hermes skills ship is a
   separate owner pick; the "stay excluded" list above is the recommended floor.
2. **frontend-skills licence.** Add a LICENSE file to saulbuilds/frontend-skills and record an
   origin and licence per skill (marketing and design skills have none) before the bundle ships.
3. **ToB attribution.** Confirm that the bundle ships the CC BY-SA notice with a "files stripped"
   change note, and that ShareAlike scope is acceptable (D-20 follow-through).
4. **Relevance exclusions.** Confirm or overturn the six merit-based ToB exclusions (`second-opinion`,
   `devcontainer-setup`, `let-fate-decide`, `interpreting-culture-index`,
   `claude-in-chrome-troubleshooting`, `skill-improver`).
