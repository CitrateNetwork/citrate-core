# Skill intake, 2026-10-01: the hermes-fork rewrite (HUP-S3.2)

The 2026-09-30 review excluded all 174 hermes-fork skills because the runtime loader refused
their frontmatter (nested `metadata.hermes.*`, and keys such as `platforms`, `author`, `tags`,
`requires`). US-3.2 AC2 asks for one format and one loader for every skill source.

## Decision applied (default, owner may change it)

The loader stays strict. Both hermes sources carry `"intake_rewrite": "flatten-frontmatter"` in
`intake.json`. For a skill the loader refuses, `scripts/skills-lock.mjs` rewrites the frontmatter
once with `scripts/skill-intake-rewrite.mjs`:

- `name`, `description`, `license`, `compatibility` and the tolerated extension keys
  (`version`, ...) stay at the top level.
- Everything else moves into `metadata` as a string: `metadata.hermes.tags` becomes
  `hermes-tags: "Research, Papers"`, a list of maps becomes JSON, `platforms` becomes
  `"linux, macos, windows"`. `metadata.intake-rewrite: flatten-frontmatter` marks the file.
- The body is kept byte for byte. Anything the rewrite cannot represent faithfully (anchors,
  aliases, tags, flow maps, a value over 1,024 characters, a key twice) is refused, and the skill
  stays excluded.
- The rewritten text must pass the same strict check as the loader (the JS port in
  `skills-lock.mjs`), including the name-matches-directory rule.

`skills.lock` keeps `skill_md_sha256` as the upstream hash (what the corpus build and a re-review
check against the checkout) and adds `intake_rewrite` and `shipped_skill_md_sha256` (what the app
ships and the sidecar verifies). `scripts/stage-skills-bundle.mjs` applies the same rewrite and
checks the shipped hash.

- **129 hermes skills now ship** (all rewritten), on the same default policy the 2026-09-30 review
  applied to the other sources: a loader-valid skill with no red flag is admitted, scripts and
  executables are stripped.
- **24 are excluded pending review**: they carry a red flag (`safety-disable`, `pipe-to-shell`,
  `credential-path`, `exfil-endpoint`) that nobody has reviewed yet. Each has a recorded decision
  in `intake.json` that says so.
- **1 is excluded on a name collision**: `hermes-optional/creative/hyperframes` has the name of the
  admitted `frontend-skills/hyperframes`; one loader source cannot hold both.
- **20 still fail the loader after the rewrite**, so they stay excluded: 17 whose `name` differs
  from their directory (mostly `mlops/*`), 2 over the 64 KiB `SKILL.md` cap
  (`research/research-paper-writing`, `mlops/pytorch-fsdp`), and `productivity/here-now`
  (`name: here.now` is not a valid skill name).

The whole lock: 296 skills, 240 ship (193 as-is, 45 stripped, 2 script-to-capsule), 56 excluded.
Staged on 2026-10-01 (`node scripts/stage-skills-bundle.mjs build`): 240 skills, 1,055 files,
8,690,842 bytes; the runtime's locked loader loaded all 240 with no refusal.

## Owner decisions

1. **The rewrite itself** (default applied above). The alternative is to widen the loader to
   nested metadata; that grows the strict grammar the sidecar parses for every third-party file.
2. **Applicability.** The default policy admits a loader-valid, unflagged skill without a human
   reading it. Several admitted hermes skills drive tools Hermes on Citrate does not have
   (`terminal`, `delegate_task`, `web_extract`) or apps outside every track (for example
   `apple/*`, `gaming/*`, `smart-home/*`). They surface only when a request matches them (at most
   five per turn), but a content pass by a person, recorded as decisions in `intake.json`, is
   still the S3.6 standard. Default until then: shipped.
3. **The 24 flagged skills** stay out until someone reviews them.
4. **Name fixes upstream.** The 17 name-versus-directory skills would load if their upstream
   renamed the directory or the name; the rewrite does not rename skills.
5. **Corpus impact.** The knowledge corpus (HUP-S3.1) ships every skill the lock admits, so the
   next corpus build includes these 129 hermes skills' text in the `skills` tenant.
