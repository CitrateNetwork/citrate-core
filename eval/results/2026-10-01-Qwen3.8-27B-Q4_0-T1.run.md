# Run record: Qwen3.8 27B Q4_0 (T1), 2026-10-01: not run

No T1 scorecard was written today. The server started and reported healthy, but every
computation failed with a Metal out-of-memory error, so no eval request could be answered and no
suite was started (the eval CLIs write nothing unless every item gets an answer).

## Serve flags: how they were chosen

The tier-driven serve plan (HUP-S1.6, `src-tauri/src/serve_plan.rs`), computed by hand from the same
inputs:

- Tier T1 target context 32,768; the model header says 262,144 trained.
- KV upper bound from the GGUF header: 65 layers x 4 KV heads x (256 + 256) x 2 bytes = 266,240
  bytes per token.
- At 32,768 tokens the need is 16.06 GB + 1.5 GiB + 8.7 GB = 26.4 GB, over the Apple Silicon
  budget (two thirds of 32 GiB = 22.9 GB). At 16,384 it is 22.0 GB, which fits. The plan serves
  16,384 tokens with `-ngl 99`.

That differs from the 2026-09-30 T1 run, which used 32,768 tokens with a q8_0 KV cache to fit.
`--reasoning-budget 1024` is kept from that run: the app ships no reasoning budget, and with
unbounded thinking this model does not finish an item inside the CLIs' 180 s timeout on this machine
(see `README.md`, "Aborted run").

## What happened

| Attempt | Flags | Result |
|---|---|---|
| 1 | `--ctx-size 16384 -ngl 99` (the plan) | warm-up and the first request failed: `ggml_metal_synchronize: command buffer failed with status 5`, `Insufficient Memory (kIOGPUCommandBufferCallbackErrorOutOfMemory)`; HTTP 500 "Compute error." |
| 2 | `--ctx-size 8192 -ngl 99` (the plan's floor) | same error |
| 3 | `--ctx-size 8192 -ngl 32` (about half the layers on the GPU) | same error |

Cause: memory on the machine, not the model or the plan. At the time the Citrate Core app's own
`llama-server` had another model resident (a 9.6 GB 27B IQ2_S file, about 9.8 GB resident), a
virtual machine and other fan-out agents' Rust builds were running, about 15 GB of memory was
already wired, and 30 of 31.7 GB of swap was in use. The 2026-09-30 T1 run succeeded when the app's
server held a 4.7 GB model. The app's server was left running: it is the owner's session, and
stopping it was not part of this task.

The serve plan sizes the context against total memory, which is right for the app (it runs one
model). It does not and need not account for a second, separate `llama-server` such as an eval
run.
