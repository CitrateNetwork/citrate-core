# Accessibility audit: pop-outs, approval cards, verdict cards (HUP-S10.6)

Scope: the pop-out framework (`src/popout/PopoutRoot.tsx`), the Activity monitor pop-out
(`src/popout/ActivityMonitor.tsx`), the approval dialogs (`SignatureCeremony` and
`WalletReviewModal` in `src/shell/Chrome.tsx`), the approval cards and HIC banner
(`src/shell/ApprovalCardView.tsx`) and the deploy gate verdict card (`src/shell/DeployGateCard.tsx`).
Target: WCAG 2.2 level AA.

Pop-out design and security model: see [POPOUT_WINDOWS.md](POPOUT_WINDOWS.md). This document only
records the accessibility checks and their results.

## Tooling

| Tool | Where | Notes |
|------|-------|-------|
| axe-core 4.13 (dev dependency) | `src/a11y/axeHarness.ts` | Runs inside vitest over real jsdom renders. Tags: wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa, best-practice. |
| Token contrast check | `src/a11y/contrast.a11y.test.ts` | Reads `src/styles/tokens.css`, composites alpha colours, computes WCAG contrast ratios. Replaces axe's colour-contrast rule, which cannot run in jsdom (no layout, no `var()` resolution). |
| Keyboard and structure tests | `src/a11y/popouts.a11y.test.tsx`, `src/a11y/approvalDialogs.a11y.test.tsx` | Focus order, focus trap, Escape, focus restore, landmarks, names, live regions. |

Not available on this machine and therefore not run: a real-browser axe pass (Chromium for
testing is not installed) and a manual VoiceOver/NVDA pass. Both are listed under "Remaining".

## Results

Every finding below was first captured by a failing test, then fixed. All tests pass after the
fixes (`npx vitest run`: 114 files, 1095 passed, 9 skipped at the build; 1098 passed after the review follow-up).

### Pop-out framework and Activity monitor

| Check | Before | Fix | Test |
|-------|--------|-----|------|
| axe-core, monitor idle / running / stopping / unknowns | pass | none needed | `popouts.a11y` axe block |
| Landmark and heading | fail: no `<main>`, title was a `<span>` | `<main aria-labelledby>` named by an `<h1>` | "is a main landmark named by its level-one heading" |
| Window (document) title | fail: never set | `document.title` = pop-out title | "names the window after the pop-out" |
| Not built / waiting / failed states | fail: bare `<div>`, waiting text not announced | each state is a `<main>` with `<h1>`; waiting is `role="status"`, failure is `role="alert"` | three PopoutRoot tests (plus axe on each) |
| Stop button: first in tab order, accessible name | partial: name was the visible word only; why it was disabled lived in `title` | `aria-label` says what it does or why it cannot be pressed (contains the visible text) | two Stop tests |
| Fact rows (Model, Tier, Context, ...) | fail: label and value were unrelated spans | each row is `role="group"` named by its label | "each fact row is a group named by its label" |
| Tool-call list | fail: unnamed list | `<ul aria-labelledby>` the "Tool calls" label; state is text (`running`, `done`), not colour alone | "the tool-call list is named ..." |
| Live regions | pass: only the "why" line is `aria-live="polite"`; the per-second clock is not announced | none needed; pinned by a test | "the why-am-I-waiting line is a polite status ..." |
| Inline motion | pass | none needed; pinned | "decorative separators and the clock carry no motion" |

### Approval dialogs (SignatureCeremony, wallet review)

Both dialogs now render inside a new `ModalDialog` frame (`src/shell/ModalDialog.tsx`).

| Check | Before | Fix | Test |
|-------|--------|-----|------|
| axe-core, ceremony with diff / command / fields + HIC / warning + queue / busy / done | pass | none needed | `approvalDialogs.a11y` axe block |
| axe-core, wallet review decoded + chain card + HIC / raw calldata / deploy gate | pass | none needed | same |
| Dialog semantics (SignatureCeremony) | fail: no `role="dialog"`, no `aria-modal`, no name | named by its `<h2>` title, described by the "requested by" line | "is a modal dialog named by its title ..." |
| Dialog name (wallet review) | partial: `aria-label` only | named by its "You are about to sign" `<h2>`, described by the subtitle | "is named by its heading" |
| Initial focus on the safe choice (T2) | pass: Decline / Reject | kept, now via `data-autofocus`; Approve is never default-focused | "focus starts on Decline / Reject, never on Approve" |
| Focus stolen on re-render | fail: the focus ref ran on every render, so ticking the raw-calldata checkbox (or any store update) threw focus back to Reject / Decline | initial focus applies once per request and phase (`focusKey`) | "a re-render ... does not pull focus back", "ticking the raw-calldata acknowledgement keeps focus" |
| Focus trap | fail: Tab walked out to the page behind the dialog | Tab / Shift+Tab wrap; focus that lands outside is pulled back in; with two dialogs open only the one drawn on top (highest z-index, so the wallet review over the ceremony) traps, and a dialog closing underneath does not pull focus away from it | three Tab tests, plus the stacked-dialog tests added in review |
| Escape | fail: no keyboard dismissal | Escape declines (ceremony, review phase only) or rejects (wallet review). Escape never approves. In the ceremony it does nothing while signing is in progress. The wallet review has no in-progress state yet, so Escape there behaves exactly like the Reject button for as long as the dialog is open. A held key (auto-repeat) is ignored, so one press resolves one request. Pending owner sign-off on keeping Escape as a decline path | two Escape tests; the HIC source tripwire in `hicApproval.test.ts` now also fails if any `onEscape` handler approves |
| Focus restore on close | fail: focus fell to `<body>` | focus returns to the element that had it before the dialog opened | "focus returns to where it was ..." |
| Signing progress | fail: step state shown by colour only, not announced | steps region is `role="status"`, each step carries screen-reader text (done / in progress / waiting); the loader and check marks are `aria-hidden` | "signing progress is announced politely ..." |
| "Witnessed" result and queue count | fail: silent | `role="status"` | covered by axe + structure tests |

### Approval cards and verdict cards

| Check | Before | Fix | Test |
|-------|--------|-----|------|
| Diff card scroll area | fail: a scrollable `<pre>` was not keyboard reachable | `tabIndex=0`, `role="region"`, named "Changes to <path>" | "the diff is a named, keyboard-scrollable region" |
| Diff lines not colour-only | pass: `+` / `-` prefixes carry the meaning | none needed | existing `approvalCards.render.test.tsx` |

| Deploy gate verdict card | fail: verdict only visible text in a coloured header | `role="group"` named "Deploy gate: READY / NOT READY"; each item starts with the word pass or fail | "is a group named with its verdict ..." + axe on READY / NOT READY / no record |

### Contrast (both registers)

Pairs checked: `--tx-1/2/3` on `--srf-0/1/2`, `--ok` on `--ok-bg` and `--srf-1`, `--warn` on
`--warn-bg` and `--srf-2`, `--danger` on `--danger-bg` and `--srf-1`, `--accent-text` on
`--srf-0/1/2`, `--tx-1` on `--ok-bg` and `--warn-bg`, and every ceremony origin pill colour on the
white dialog panel. Threshold 4.5:1 (all of this text is small).

Instrument (dark) register: every pair passes unchanged (lowest: `--tx-3` on `--srf-2`, 4.6:1).

Charter (light) register: four tokens failed and were darkened. Hue is unchanged; only lightness
moved, by the smallest step that reaches AA on every surface the token is used on.

| Token | Before | Worst ratio before | After | Worst ratio after |
|-------|--------|--------------------|-------|-------------------|
| `--tx-3` | `#84867f` | 3.3:1 on `--srf-0` | `#6b6d67` | 4.6:1 |
| `--ok` | `#4f8a05` | 3.7:1 on `--ok-bg` | `#467904` | 4.6:1 |
| `--warn` | `#b07b00` | 3.3:1 on `--warn-bg` | `#8f6400` | 4.7:1 |
| `--accent-text` | `#5a8205` | 4.0:1 on `--srf-0` | `#517505` | 4.6:1 |

These are global charter tokens, so every charter surface gets slightly darker captions and
status text. Pending owner sign-off on the exact values (the test pins the AA floor, not the
values, so a designer can pick other shades that pass).

### Reduced motion

`tokens.css` carries one `prefers-reduced-motion: reduce` rule that cuts every animation and
transition to 0.01 ms on every element; the dialog fade (`cc-fade-up`) and the "Witnessed" stamp
(`cc-stamp`) are named classes that rule covers, and `LoaderMark` already renders a static mark
under reduced motion. A test pins the rule and checks that the S10.6 surfaces add no inline
animation, transition or `requestAnimationFrame` of their own.
