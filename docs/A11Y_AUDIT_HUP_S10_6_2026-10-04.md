# Accessibility audit follow-up: real-browser axe pass (HUP-S10.6)

This follows [A11Y_AUDIT_HUP_S10_6_2026-10-01.md](A11Y_AUDIT_HUP_S10_6_2026-10-01.md), which is
not edited (Rule 3). That audit ran axe-core under jsdom only and listed two open items: a
real-browser axe run with the colour-contrast rule on rendered pixels, and manual screen-reader
passes. This document closes the first and gives exact steps for the second.

It also covers the Activity monitor sections added on this branch for US-7.4 AC1 (Speed, Plan,
Approvals, Checks, and the daemon token source line).

## Tooling

| Tool | Version | Notes |
|------|---------|-------|
| Chromium (Chrome for Testing, headless) | 153.0.8010.12 | The build already in `~/Library/Caches/ms-playwright/chromium-1243` on this Mac. Nothing was added to `package.json`. |
| playwright-core | 1.58 | Installed in a scratch folder only, passed in with `PLAYWRIGHT_CORE`. |
| axe-core | 4.13.0 | The repo's own dev dependency (`axe.min.js` injected into each page). |
| Runner | `scripts/a11y-browser.mjs` | Builds `scripts/a11y-browser/scenes.tsx` with the repo's Vite and the app's real stylesheet (`src/styles/index.css`), serves it on a loopback port, opens each scene, waits for entrance animations to finish, runs axe. |

Rules: the same tags as the jsdom harness (wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa,
best-practice) with **color-contrast on**. The two page-level rules the jsdom harness also turns
off (`page-has-heading-one`, `region`) stay off: each scene is one surface of the app, not a page.

Each scene runs twice: at a 1024 x 900 viewport at 100%, and at 200% zoom (512 x 450 CSS pixels,
device scale 2), which is the WCAG 1.4.4 resize check.

To repeat it:

```sh
npm i --prefix /tmp/pw playwright-core@1.58
PLAYWRIGHT_CORE=/tmp/pw/node_modules/playwright-core node scripts/a11y-browser.mjs --json /tmp/a11y.json
```

Set `CHROMIUM_PATH` if no Chrome for Testing build is in the Playwright cache.

Two things the first run surfaced, both about the harness, not the app:

1. **The deploy gate card alone has no `<main>`** (`landmark-one-main`, moderate). In the app the
   card is always inside the main window's `<main>` or a dialog; the scenes now place it in one.
   No app change.
2. **Mid-fade frames.** The dialogs open with a 0.4 s fade (`cc-fade-up`). Sampled during the
   fade, the wallet review's HIC banner text measured 4.45:1 (blended colours `#916603` on
   `#fdefc3`); settled, it passes. The runner now waits for `document.getAnimations()` to finish
   before it runs axe. A member sees the low-contrast frames for well under half a second, and
   not at all with reduced motion (the `prefers-reduced-motion` rule from the first audit cuts
   the fade). Recorded, no change made.

## What this pass does not prove

- It runs Chromium, not the app's own webviews: WKWebView on macOS, WebKitGTK on Linux, WebView2
  on Windows. Playwright's WebKit build is not installed here. Colour and layout are the same
  stylesheet, but a packaged-app check on each webview is still owed.
- axe checks structure and contrast. It cannot hear what a screen reader says or judge reading
  order and verbosity. The steps below are for people.

## Screen-reader passes (human; not done)

### VoiceOver on macOS (packaged app)

1. Build and open the packaged app (`npm run tauri build`, then open
   `src-tauri/target/release/bundle/macos/Citrate Core.app`).
2. Turn on VoiceOver: Command + F5. Set the verbosity to default (VoiceOver Utility > Verbosity).
3. **Activity monitor.** From the main window, open the Activity monitor pop-out. Expect: the
   window is announced as "Activity monitor", the first Tab stop is the Stop button and its name
   says what it does ("Stop the running turn") or why it cannot be pressed. Use VO + U to open
   the rotor: the Landmarks list has one "main"; the Headings list has "Activity monitor".
   Start a chat turn that calls a tool: the "why am I waiting" line is read once per change, the
   elapsed clock is not read every second. Check Speed, Context, Plan, Approvals and Checks are
   each read as a labelled group or list with their state in words.
4. **Approval card.** Ask Hermes to add a row to a Google sheet (or any write tool). Expect: focus
   moves into the dialog, the dialog is announced by its title, focus starts on Decline, Tab and
   Shift + Tab stay inside, Escape declines and never approves, and focus returns to where it was
   after the dialog closes. With a HIC-required call, the banner is announced as an alert with
   its reason.
5. **Wallet review.** Trigger a contract deploy proposal. Expect the same dialog behaviour, the
   raw-calldata acknowledgement checkbox keeps focus when ticked, and the deploy gate verdict is
   read as "Deploy gate: READY" or "NOT READY" with each item starting with pass or fail.
6. Record each step as pass or fail, with the exact words VoiceOver said for any fail, in a new
   dated follow-up audit next to this one.

### NVDA on Windows (packaged app; Windows machine needed)

1. Install the Windows build (`npm run tauri build` on Windows, MSI under
   `src-tauri/target/release/bundle/msi/`) and NVDA 2025.x or newer.
2. Start NVDA (Control + Alt + N). Use browse mode for reading, focus mode inside dialogs.
3. Repeat steps 3 to 5 above. NVDA keys: Insert + F7 opens the elements list (landmarks,
   headings), Tab / Shift + Tab for focus order, Escape in the dialog.
4. Also check WebView2 announces the dialog role on open (NVDA says "dialog" and the title).
5. Record results the same way.
