# 0.5.3: the network release for r1007

0.5.3 is the build that syncs r1007. Everything except the r1007 values is in this repo now, so
cutting it is: fill one file, run one command, regenerate two derived files, bump the version.
Until the values exist, every release check refuses r1007 by name.

The plan, decisions and gates are in the federation planset (link, don't copy): CORE-N1..N6 in
`03_CORE_AGENT_DAEMONS.md`, S4 (genesis, bring-up, soak) and S5 (release) in
`05_SPRINTS_AND_WPS.md`, decisions CV-1..CV-14 in `adrs/ADR-2026-11-03-chain-convergence-r1007.md`.
The updater plan is [053-UPDATER.md](053-UPDATER.md); the clean-machine cold sync is
[053-COLD-SYNC.md](053-COLD-SYNC.md).

`apply` refuses while anything is pending, on any malformed value (zero or reused genesis, a
chain parameter set that is not exactly the node's thirteen positive integers, an undo window
above the profile's member retention, an RPC that is not https, a short rev, a bootnode on another host or a missing one, a macOS or Linux aarch64 node asset not named after the rev,
a pin with no evidence), and writes nothing in that case. `scripts/network-cut.test.mjs` covers
every refusal and the full apply on a copy.

**core#586 (reproducible builds): still open, unmerged.** It adds opt-in
`build.reproducible` to `build-component.sh` and `scripts/check-reproducible.sh` (two clean builds
in two roots must match). Without it the node pins stay "fixed asset" pins: the bytes built once,
uploaded, and verified by digest (`docs/RELEASE_LINUX.md`, chain#427). The cut works either way;
with #586 merged first, set `build.reproducible: true` on `citrate-node` and record the
check-reproducible result in each target's `evidence`.

### The node config the r1007 node accepts

The r1007 node compiles chain parameters for its block 0 and refuses to start when the node
config's `[checkpoint] interval`, `committee_size` or `vote_depth` differ from them. The member
template's `[checkpoint]` happens to match today's values through the node's defaults, but a
default is not a pin: the cut writes the three values into the profile (`nodeCheckpoint`) and
`network_profile::render_node_network` writes all three into `node.toml` explicitly. Profiles
without `nodeCheckpoint` (alpha-r1005, r1006) keep the template's section byte for byte, so
nothing changes for 0.5.2 networks. The same rule is in `scripts/network-profile.py`,
`src/network/profile.ts` and the cold-sync harness's renderer.

Proof: `scripts/network-cut.test.mjs` applies a filled cut built from the chain's candidate r1007
values (`fixtures/network-cut/r1007-candidate.json`, marked candidate: the block-0 hash changes
when the chain integrates its r1007 lanes) and checks it writes exactly
`fixtures/network-cut/r1007-candidate.applied.json`; `network_profile_tests.rs` renders the member
node config from that profile and runs the node's start-up comparison against the candidate
parameters (and shows a differing value is caught).

The GUI does not build block 0 itself: the bundled node does, and the node's own genesis build
publishes the state root rule first. The app's part is the r1007 `nodeGenesisProfiles` entry,
which the cut writes.

## N2: the r1007 profile

Set now: chain id 40204 (permanent), `nodeNetwork` testnet, `https://rpc.citrate.ai` (confirmed
by the cut's `rpcUrl`),
`https://explorer.citrate.ai`, `https://faucet.citrate.ai`, `addresses/40204.json`,
`memberPruneRetain` 10,000. Null until the cut: `genesisHash`, `genesisProfile`, `bootnodes`,
`addressBookSha256`, `minChainRev`. `active` stays `r1006` on main, because CI runs
`check-network-profile.sh --release` on every push and main must stay a working build.

r1006 stays a known profile after the cut, so a data dir from it is still named (`chain.r1006.bak`)
and the webview can say which network it was. The cut marks it `retired`; a retired profile is
refused like an unset one (no node start, no signature, in Rust, the webview and the checks), and
`check-network-profile.sh` fails on any build whose active profile is retired.

Today `scripts/check-network-profile.sh --release --require-active r1007` fails ("active profile is
'r1006', required 'r1007'"). Flipping `active` by hand also fails: the unset values are named and
the message points at the cut, and while the cut's profile is active the check runs
`network-cut.py check --release` too.

## N3: a 0.5.2 data dir on r1006

On the first start of 0.5.3 the node data dir still belongs to r1006. Before the node starts
(`node_genesis::reconcile_genesis`, under the chain database lock):

- every RocksDB file moves, byte for byte, into `node/chain.r1006.bak/` (0700). The name comes from
  the profile whose genesis the old marker names; an unknown genesis uses its first 10 characters,
  none uses `unrecorded`. A second switch from the same network gets `chain.r1006.bak-2`.
- the backup's name is in the migration intent before the first file moves, so a crash part way
  through finishes into the same backup; the marker is still the one commit point;
- `node.toml` is set aside as `node.toml.0xa3651a27` (member edits kept) and a new one is rendered
  from the r1007 profile;
- the wallet vault, keychain slots, IPFS pins, Store models, Hermes settings, invites, daemons and
  node keys are not touched;
- the member is told the chain was reset, where the old settings and the old chain data are, and
  that the backup folder can be deleted to free space.

Proof: `node_genesis` tests `n3_*` and `upgrade_r1007_tests` (fixtures/upgrade-v0.5.2-r1006).

Disk: the move is a rename inside the data dir, so it costs no space at the switch, but the r1006
chain stays on disk until the member deletes it (tens of GB on a full member). Node › Advanced
"Old network data" lists each `chain.<network>.bak` with its size and removes one after a single
confirmation (`node_old_network_data`, `node_remove_old_network_data`, `chain_backup.rs`). Rust
removes only a real directory of that name directly in the node data dir, holding only chain
database files, at the size the member confirmed, while no switch is unfinished; it refuses every
other path (traversal, absolute, symlinks, key or config files, the current chain) and removes
files one by one, never recursively.

## N4: sync truth

`node_status` now carries, from the node's local RPC, `syncState` (`citrate_nodeIdentity`) and
`peerTips` (`net_peerInfo[].headHeight`). Both are feature-detected: a node without them gives
nothing, and the words fall back to today's rule. The Node page word (`nodeWords.ts`):

- **Wedged** (`syncState: wedged`) beats every height comparison;
- **Synced** only within 5 blocks of every view: the public RPC head (fresh), the peers' quorum tip
  (the height a strict majority of at least two reporting peers are at or above) and the node's
  own `highestSeen`;
- **Sync unknown · this node is ahead of the network head** when more than 5 blocks above every
  view (core#589 item 1);
- a wedged node's `syncPct` is unknown (-1), never 100.

Chain follow-up for the lead: today's node keeps each peer's `head_height` (`PeerInfo`) but
`net_peerInfo` does not return it, so the quorum view stays empty until the chain adds
`headHeight` to `net_peerInfo` (read-only RPC, no consensus change). Until then "Synced" is the
public head plus the node's own `highestSeen`.

core#589 item 2 (old rewards figures after a bond key change) is not in this PR.

## N5: member pruning (decision recorded)

Default for r1007 members: **pruned, retention 10,000 blocks**, the undo window (ADR CV-7a:
undo window = retention; the r1007 chain keeps reorg undo records for 10,000 heights).
**Confirmed by the owner (CV-7a accepted, 2026-11-07, relayed by the MAC lead).** It is one value
(`memberPruneRetain` on the r1007 profile; removing it restores full history).

What it does: the r1007 profile renders `[storage] pruning = true`, `keep_blocks = 10000`.
Profiles without the key (alpha-r1005, r1006) keep full history, so this changes nothing for
0.5.2 networks. A retention below 10,000 is refused everywhere.

What it does not do: the DAG-store prune (`CITRATE_DAG_PRUNE_RETAIN`) stays off. The app's guard
test against it exists because of the r1005 cold-sync wedge at 54,600; turning it on for r1007
needs the chain lead's confirmation that r1007's bounded merge scoring makes it safe, and then a
deliberate change of that guard.

Consequence to plan for: pruned members cannot serve a cold sync from genesis, so the fleet's
boot, rpc and indexer nodes must stay full-history.

## Cutting 0.5.3 (runbook)

1. **Values**: fill `release/network-cut.json` from the S4-1/S4-2/S4-3 records (genesis, keys,
   book) and the three node builds (N1); empty `pending`.
2. `python3 -I scripts/network-cut.py apply`.
3. `cargo update -p citrate-wallet-core -p citrate-commd` (Cargo.lock to the chain rev).
4. Copy the frozen canonical book and run `scripts/sync-addresses.py --book <it> --genesis <hash> --rpc https://rpc.citrate.ai`.
5. Version 0.5.3 (`package.json`, `src-tauri/Cargo.toml`, `tauri.conf.json`, `release/components.json` `release`), notices and changelog, as for 0.5.2.
6. Checks: `python3 -I scripts/network-cut.py check --release`, `scripts/check-network-profile.sh --release --require-active r1007`, `node scripts/component-pins.mjs check`, `cargo test --workspace --locked` (droplet), `npm test`.
7. Federation (Rule 11/12): move `[repos.citrate-chain]` and the citrate-core `[[drift]]` rows in
   `citrate-federation/manifest.toml` to the chain rev in the same change set.
8. G6 cold sync (N6) on macOS and Linux with `--expect-fingerprint`, then the updater path
   ([053-UPDATER.md](053-UPDATER.md)).

**The cut waits for the public chain rev.** The app's Cargo git dependencies
(`citrate-wallet-core`, `citrate-commd`) and `build-sidecar.sh` fetch from public `citrate-chain`,
and `component-pins.mjs check` requires them to equal the node rev. The r1007 chain rev lands on
public citrate-chain at the r1007 launch, as a signed merge of the advisory line (as 56cc2bc8 was
for 0.5.2); steps 1 to 3 run after that merge, never against an unpublished rev.

**Open input:** the aarch64 Linux builder for `node.aarch64-unknown-linux-gnu` (and its
PROVENANCE record) is an open owner question; the cut cannot complete without it. One candidate
(2026-11-08): the `release-linux-aarch64` job's dry run on `ubuntu-24.04-arm` builds the node at
the pinned rev and keeps the bytes with the run ([RELEASE_LINUX.md](../RELEASE_LINUX.md#linux-aarch64-in-ci-release-linux-aarch64)).
