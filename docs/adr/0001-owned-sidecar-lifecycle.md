# ADR-0001 — Bound sidecar work and acknowledge lifecycle transitions

## Decision

Propose one app-owned lifecycle cell per shared sidecar, retaining the existing std monitor as its sole process/control writer. Order pending validation, replacement and Stop with a distinct control-intent sequence; register owned spawn/publication tickets before releasing admission locks. Separate process existence from application readiness; reset health retry budgets only after a fresh successful-health window; retain actual probe/reader ownership after an observer timeout; and bound retained logs by encoded bytes before allocation. Managers serialize replacement and generation-owned credential cleanup through the same cell. Add a small app shutdown coordinator, an independently scheduled native deadline publisher and revisioned cached status snapshots; navigation owns subscriptions, not shared services.

No async-runtime migration, generic durable OperationRegistry, new process-management dependency, or automatic signing is proposed. The shared service set remains Node, node agent, memory, llama, IPFS, Hermes, Comms and Cluster. Preserve prerequisites, binary resolver, cold-start grace, ceremony and custody boundaries. A custom synchronous literal-only resolver and TCP connector retain health HTTP work in its admitted worker; exact-pin the existing ureq 3.3.0 interface and re-gate any adoption because that API is unversioned. Literal URLs alone do not satisfy this decision.

For Unix, propose opt-in containment of cooperating descendants with an owned session/group initialized before execution and existing libc. Retain the unreaped leader through final group actuation via typed, freshly zeroed WNOWAIT polling; permanently close actuation before reaping and use conservative supported-platform absence observation afterward. Require sole-reaper/process-wide compatibility before enablement. Never signal by executable-name search or reuse a reaped numeric identity. Windows Job ownership is PARKED pending its own native gate; direct-child capability remains explicit. This ADR does not certify Windows tree cleanup, escaped Unix descendants or post-crash recovery. Full cross-platform cleanup claims cannot ship behind this design alone.

This is a content-locked design proposal, not an accepted federation decision, an implemented fix or release approval. The canonical private planset could not be read; owner reconciliation and adoption remain required. SPEC-001 defines evidence, future acceptance, migration and parked work.

## Why

The supervisor is the common lifetime and resource boundary for eight services. Correcting that contract once reduces duplicated recovery logic and makes every manager report the same meaning of accepted, ready, stopping and incomplete. Useful process/backoff/log controls already exist; retaining the native owner avoids replacing working architecture to fix narrower contract failures.

Immediate benefit: bounded actual probe admission, predictable stop/retry behavior, no old cleanup acting on a replacement, and truthful readiness. Long-term benefit: reusable service recovery and bounded diagnostics without a durable operation system. It unlocks testing cold loads and failed shutdowns consistently and safely adding another sidecar with an explicit readiness/ownership profile.

The cost is a cross-cutting status/control migration, short lifecycle synchronization, byte-aware drains and native-platform acceptance. Availability deliberately decreases when an uninterruptible worker consumes its one reserved slot: quarantine is preferable to silently accumulating work. Performance defaults remain proposed budgets until measured on packaged target platforms.

## Adversarial Defense

The first independent architecture review returned REVISE DESIGN after reproducing the baseline evidence. Its five blocking attacks are answered below; v2 confirmed those five resolutions but found one blocking deadline-execution gap and two contract clarifications. Fresh independent v3 review returned APPROVE DESIGN for the scoped proposal, with no blocking design contract failure. It verified the complete candidate contracts, unchanged reproduction inputs, eight-story dependencies and pinned public ownership APIs. Adoption and native acceptance remain outstanding. Its essential future proofs cover atomic arming/supersession/completion/expiry and delayed expired-token delivery during receipt turnover, plus publisher creation failure/unexpected termination with unavailable admission and no replacement. These are mandatory implementation acceptance, not optional performance checks. These answers specify future acceptance, not an implemented correction.

The subsequent Comms merge reopened research: current CancelSynchronousIo does not attest completion of the pinned overlapped pipe path, and foreground joins alone miss library linger workers. The design requires eight retained foreground slots and a source-verified public no-clone consuming handle path, with Windows native transport acceptance still PARKED.

Proposed numeric budgets require packaged measurements. The metadata split is defended as a transparent validation contract, with owner adoption still pending; direct original ADR strict check is never claimed.

## Interfaces

The normative contract is in SPEC-001. Service identity is one of eight fixed owners. Sequence/generation/revision counters cross JavaScript as numerically compared decimal strings, avoiding u64 precision loss. A snapshot carries appEpoch, controlIntentSequence, serviceGeneration, childIncarnation, revision, desiredState, phase, readiness, freshness, owned resources, containment capability, retry/resource counters and redacted reason. Credential values/crash payloads are not status identifiers.

New Start/Stop/Shutdown controls return Accepted, AlreadySatisfied, RejectedClosing, Busy, ObservationUnknown or Quarantined with a bounded ephemeral token; superseded/expired observation stays explicit. Accepted is not completed. Repeated Stop joins the same completion. Complete attests only its named scope and outstanding tickets; missing observation is Incomplete. Legacy controls retain explicit spawn-versus-terminal-stop semantics, with bounded await slots and honest errors. Observer deadlines never imply cancellation. Replacement waits for matching teardown; private generation files are cleaned only by their owner.

The app closes admission before concurrent drain under one monotonic absolute deadline. Stop suppresses new spawn admission even in Off/Backoff; already admitted calls remain owned. Wake failure reports unknown observation. Native state owns services; React owns a cached immutable subscription/startup epoch. Retain one actual raw status promise across epochs rather than add a native listener on the affected 2.11.5 pin. Quit, restart and Windows updater installation coordinate before final action; the current special restart code and updater direct exit cannot be intercepted reliably by an asynchronous ExitRequested handler alone.

## Scalability

The population is fixed at 8; provision one retained monitor, at most 2 readers and one actual probe slot per service, plus one crash sink, coordinator and independent deadline publisher (35 supervisor-owned threads). Validation/preflight uses the monitor and sequential child slot. Timeouts do not release slots before completion. Control storage is one descriptor/coalesced wake and one active/completed receipt/service; compatibility await slots are separately bounded. No hidden DNS workers/proxy health transport is allowed. Selected Windows Comms adds at most 8 foreground workers (43 in that combined scope), with up to 64 MiB proposed encoded payload buffers; no hidden linger transfer is permitted. This is not total-app thread/RSS certification.

Proposed initial limits are 16 KiB per partial/log line, 256 KiB retained ring and 500 entries per service, 64 KiB per log snapshot with at most 2 concurrent serialization requests app-wide, 8 KiB per crash record, 64 queued crash records and 2x 16 MiB rotated crash files per service. These are reviewable defaults, not measured optima. Bound metadata and diagnostic counters as well. App shutdown starts owners concurrently and never sums eight independent stop budgets. Filesystem/OS nonprogress becomes incomplete/quarantine, not an infinite wait or a guaranteed cleanup claim.

## Rejected

A generic durable OperationRegistry/event bus is unnecessary for ephemeral service status and would create recovery/retention semantics. Broad Tokio conversion is not required to fix these shared invariants. Releasing a worker permit on timeout, collecting an unbounded line before truncation, treating child exit or pipe EOF as tree-empty, and treating coarse Running as attested readiness fail the intended contract.

Stock process-wrap 10.0.1 is PARKED as a complete cross-platform cleanup solution: std Job wrapper disables kill-on-close by default, has unbounded wait, and its try_wait does not expose Job emptiness. Its internal completion-port waiter also does not require ACTIVE_PROCESS_ZERO. These are pinned source observations, without Windows execution; they do not disparage its narrower ownership-mechanics utility.

Public group-message retention, durable financial-operation retry/replay, agent session cancellation, signing-budget policy, unrelated store bugs and automatic update/deployment changes remain outside this decision.

## Re-evaluate When

Re-gate for a growing/dynamic job population that exceeds fixed-service budgets, a genuine persistent-operation requirement, a new process/transport dependency, an altered ceremony boundary, or measured packaged performance that invalidates proposed limits. A noncooperative loopback adapter must be constrained or isolated before automatic restart is re-enabled.

Windows containment reopens only with a fresh decision on native mechanics/dependency, suspend→owned-Job assignment→resume, no breakaway, kill-on-last-handle-close policy, authoritative ActiveProcesses observation and bounded native tests. Unix full-cleanup claims reopen for daemon/session escape or observed inability to safely retain ownership through group cleanup. Canonical private planset access or an explicit owner deviation decision is required before adoption; owner review must resolve this proposal's cross-cutting DTO and retry-policy changes.
